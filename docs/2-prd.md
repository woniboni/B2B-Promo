## 1. 제품 개요/배경

식자재 유통사가 B2B 거래처(외식업체·급식업체 등)에게 진행 중인 프로모션(가격 할인, 샘플 증정, 신제품 시식, 1+1)을 안내하고 참여 신청을 받는 웹 애플리케이션이다.

**해결하려는 문제**: 현재 프로모션 정보는 영업 담당자의 개별 안내, 전화, 카톡 등 흩어진 채널로만 전달되어 거래처가 놓치기 쉽고, 참여 의사를 남길 공식 창구가 없다. 관리자 역시 프로모션을 체계적으로 등록·관리하고 거래처 반응(참여 현황)을 확인할 수단이 없다.

B2B-Promo는 (1) 관리자가 프로모션을 등록·게시·종료 관리하고, (2) 거래처 담당자가 프로모션을 조회하고 참여 신청(및 선택적으로 즉시 추첨되는 랜덤 쿠폰 이벤트 참여)을 할 수 있는 단일 창구를 제공한다.

**개발 배경**: 본 프로젝트는 3일 내 1인 개발로 핵심 기능을 완성하는 교육용 바이브코딩 실습이다. 따라서 오버엔지니어링을 배제하고, 도메인 정의서의 MVP 범위 내에서 "3일 안에 실제로 완성 가능한 범위"를 명확히 구분하는 것을 이 PRD의 핵심 목적으로 한다.

## 4. 범위 (Scope)

### 4.1 포함/제외 (도메인 정의서 MVP 범위 계승)

**포함**
- 회원가입/로그인 (거래처 담당자만 가입, 관리자는 시딩)
- 프로모션 등록·조회·게시/종료 관리
- 참여 신청/취소 (상태 전환 방식)
- 랜덤 쿠폰 뽑기 즉시 추첨 (재추첨 불가, 선착순 50명, 동시성 안전)
- 마이페이지 (정보 수정/비밀번호 변경)
- 반응형(모바일 우선/데스크탑) UI

**제외**
- 실제 주문/결제/정산
- 재고 실시간 연동
- 승인 워크플로우
- 거래처 등급별 차등가
- 포인트 적립
- 검색 기능
- 경품(쿠폰) 재고 관리
- (추가) 접근성(a11y) 대응, 다국어(i18n), 네이티브 모바일 앱, 프로덕션 배포/운영 인프라 구축

### 4.2 "3일 안에 실제로 만들 수 있는 범위" 재확인

MVP 범위 전체(9개 유스케이스)는 각각이 CRUD 수준의 단순 기능이므로 3일 내 완성이 가능하다고 판단하되, 시간이 부족할 경우를 대비해 **잘라낼 수 있는 부분(Should/Could)**을 먼저 명확히 한다. 우선순위 기준은 "도메인의 핵심 가치(프로모션 조회→신청→추첨, 관리자 관리/현황)를 시연하는 데 필수인가"이다.

- **Must (핵심 가치 시연에 필수, 반드시 3일 내 완성)**: UC-1, UC-2, UC-3, UC-4, UC-5, UC-7, UC-8
- **Should (완성도를 높이지만 시간이 부족하면 최소 구현으로 축소 가능)**: UC-6 (임시저장은 별도 화면/버튼 없이 Promotion.status 필드값 지원만으로 대체 가능)
- **Could (시간이 남을 때만, 가장 먼저 잘라내는 후보)**: UC-9 (마이페이지 정보 수정/비밀번호 변경)

우선순위 상세는 5절 표 참조.

## 6. 비기능 요구사항 (NFR)

### 6.1 반응형 UI
- 모바일 우선(mobile-first) 반응형 CSS 적용. 거래처 담당자 화면은 스마트폰 뷰포트 기준으로 우선 설계 후 데스크탑으로 확장.
- 관리자 화면은 데스크탑 사용이 주이나, 동일 코드베이스에서 반응형으로 동작해야 함 (별도 관리자 전용 레이아웃 프레임워크 도입 없이 CSS 미디어 쿼리로 대응).
- 별도 UI 컴포넌트 라이브러리 도입은 필수 아님 (3일 일정상 커스텀 스타일 최소화 권장, 필요 시 개발자 재량으로 경량 라이브러리 선택 가능).
- 접근성(a11y)은 본 프로젝트 범위에서 고려하지 않는다 (요청사항 반영).

### 6.2 성능/동시성 - 선착순 50명 쿠폰 이벤트 (BR-6, BR-7 핵심)
- **원자성 요구**: 쿠폰 이벤트 참여 신청 시 `CouponEvent.applied_count` 증가와 마감 판정(`applied_count >= 50`)은 반드시 하나의 DB 트랜잭션 내에서 원자적으로 처리한다. 동시에 다수 요청이 몰려도 정확히 50건까지만 성공하고 51번째부터는 거부되어야 한다(BR-7).
- **구현 방식(권장)**: `pg` 트랜잭션 내에서 `UPDATE coupon_events SET applied_count = applied_count + 1 WHERE id = $1 AND applied_count < capacity RETURNING applied_count` 형태의 조건부 원자 증가 쿼리를 사용하고, 영향받은 행이 0건이면 마감으로 판단해 신청을 거부한다. PostgreSQL의 행 잠금(row-level lock)이 자동으로 동시 요청을 직렬화하므로 별도의 분산 락이나 큐 도입은 불필요하다.
  - ponytail: 단일 DB 인스턴스·단일 CouponEvent 행 기준의 락 경합에 의존하는 단순 구현. 트래픽이 커져 경합이 병목이 되면 그때 큐 기반 처리로 승격.
- **중복 신청 방지**: `Application(promotion_id, partner_id)` 조합에 유니크 제약(DB 레벨)을 걸어 EX-2의 중복 신청 거부를 DB 제약으로도 보장한다.
- **성능 목표**: 실습 규모(1인 개발, 로컬/소규모 데모 환경)에서는 별도의 부하 테스트 인프라 구축은 범위 밖으로 하되, 위 원자적 쿼리 로직이 동시 요청 시 정확히 50건만 성공시키는지 최소 1개의 재현 스크립트(예: 동시 요청 N개를 병렬 실행 후 성공 건수 검증)로 확인한다.
- **추첨 확률분포 검증(BR-4)**: 추첨 로직을 최소 200회 이상 반복 호출하는 스크립트로 각 할인율(5/10/15/20%)의 실제 당첨 비율을 집계하고, 목표 확률(40/30/20/10%) 대비 ±10%p 이내인지 확인한다. 오차 범위를 벗어나면 난수 생성 로직(가중치 구간 분할)의 구현 오류로 간주한다.

### 6.3 보안 (최소 범위)
- 비밀번호는 해시(bcrypt 등)하여 저장, 평문 저장 금지.
- **인증은 JWT 기반, Access Token + Refresh Token 이중 토큰 방식을 적용한다.**
  - **Access Token**: 짧은 만료(예: 15분). 클라이언트 메모리(Zustand 전역 상태)에 보관하며, API 요청 시 `Authorization: Bearer` 헤더로 전송한다. 만료 시 매 요청마다 재로그인시키지 않고 아래 재발급 절차를 거친다.
  - **Refresh Token**: 긴 만료(예: 7일). XSS로부터 보호하기 위해 `httpOnly`+`Secure` 쿠키에 저장하며, 클라이언트 JS(Zustand/localStorage)에서는 직접 접근하지 않는다.
  - **재발급 흐름**: Access Token 만료(401) 시 클라이언트가 `POST /auth/refresh`를 호출하면, 서버가 쿠키의 Refresh Token을 검증하여 새 Access Token을 발급한다. 로그아웃 시 Refresh Token 쿠키를 즉시 삭제한다.
  - Refresh Token은 서명 검증만으로 유효성을 판단하는 상태 비저장(stateless) 방식으로 구현한다(별도 DB 저장/블랙리스트 없음).
    - ponytail: 탈취된 Refresh Token의 로그아웃 전 즉시 무효화(revocation)는 지원하지 않는 단순 구현. 필요해지면 Refresh Token을 DB에 저장하고 로그아웃/재발급 시 폐기(rotation)하는 방식으로 승격.
- 별도 OAuth/SSO 등은 범위 밖.

## 7. 기술 스택 / 아키텍처 개요

| 영역 | 선택 |
|---|---|
| 프론트엔드 | React 19 |
| 전역 상태관리 | Zustand (로그인 세션/사용자 정보 등 클라이언트 상태) |
| 서버 통신/캐싱 | TanStack Query (API 호출, 서버 상태 캐싱/재검증) |
| 백엔드 | Node.js + Express |
| DB 드라이버 | pg (PostgreSQL 네이티브 드라이버) |
| 데이터베이스 | PostgreSQL 17 |

**아키텍처 개요**
- React SPA (프론트) ↔ REST API (Express, 백엔드) ↔ PostgreSQL
- 클라이언트 상태(로그인 여부, 사용자 정보 등)는 Zustand, 서버 데이터(프로모션 목록, 신청 목록 등)는 TanStack Query로 관리해 역할을 분리한다.
- DB 스키마는 도메인 정의서 2-1절 엔티티(User, Partner, Promotion, CouponEvent, Application, DrawResult)를 그대로 테이블로 매핑한다.
- 별도 ORM 도입 없이 `pg`로 파라미터화된 쿼리를 직접 작성한다 (3일·1인 개발 규모에서 ORM 학습/설정 비용을 줄이기 위함).
  - ponytail: 쿼리가 늘어나 반복이 심해지면 그때 쿼리 빌더 도입 검토.
- 배포/운영 인프라(CI/CD, 클라우드 호스팅 등) 구성은 본 PRD 범위 밖으로 하며, 로컬 또는 단순 데모 환경에서의 시연을 전제로 한다.

## 9. 리스크 및 가정

**리스크**
- 3일·1인 개발이므로 자동화 테스트 커버리지는 최소화하고 수동 QA 위주로 진행한다. 회귀 위험이 있으나 실습 목적상 감수한다.
- 선착순 50명 동시성 로직(6.2절)은 이 프로젝트에서 가장 기술적으로 까다로운 부분이므로, Day 2 초반에 우선 구현/검증하여 일정 리스크를 조기에 해소한다.
- JWT Access/Refresh 이중 토큰 발급(6.3절)은 단일 토큰 방식보다 구현 공수가 크므로, Day 1에서 예상보다 지연되면 Refresh Token/재발급 흐름을 후순위로 미루고 만료가 긴 Access Token 단일 방식으로 우선 동작시킨 뒤 시간이 남으면 이중 토큰으로 승격한다.
- 접근성(a11y)·다국어 미고려, 배포 인프라 미구축은 실습 범위상 의도적 축소이며 실서비스 전환 시 재검토가 필요하다.

**가정**
- 관리자 계정은 회원가입 기능 없이 DB 시딩 스크립트로 생성한다(BR-2, UC-1 범위 밖).
- 인증 방식은 JWT Access/Refresh Token 이중 발급(6.3절)을 기본으로 하며, 별도 세션 스토어(Redis 등) 도입은 하지 않는다(Refresh Token은 stateless 검증).
- Partner-User 1:1 단순화, 프로모션 기간 필드 없음 등 도메인 정의서의 "알려진 제약"을 그대로 계승한다.
- KPI(2절)는 운영 단계 목표이며, 3일 실습 결과물 자체의 완료 기준이 아니다.
