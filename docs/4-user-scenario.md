## 1. 거래처 담당자 시나리오 (기본 기기: 모바일)

거래처 담당자는 외식업체·급식업체 등 현장에서 스마트폰으로 접속하는 것을 기본으로 한다(PRD 3절, 6.1절 모바일 우선).

### 1.1 회원가입 및 로그인 (UC-1)

**상황**: 거래처 담당자가 진행 중인 프로모션을 확인하려고 모바일 브라우저로 앱 URL에 접속한다.

- 사용자 행동: 로그인하지 않은 상태로 프로모션 목록 화면 접근을 시도한다.
- 시스템 반응: 모든 기능은 로그인 후에만 이용 가능하므로(BR-1), 로그인 페이지로 강제 이동시킨다(EX-5).
- 사용자 행동: 계정이 없으므로 회원가입 폼(이메일, 비밀번호, 이름, 전화번호, 거래처명)을 작성해 제출한다(BR-2).
- 시스템 반응: 계정과 거래처(Partner)를 1:1로 생성하고, 로그인 화면으로 안내한다.
- 사용자 행동: 이메일/비밀번호로 로그인한다.
- 시스템 반응: JWT Access/Refresh 토큰을 발급하고 프로모션 목록 화면으로 이동시킨다.
- 결과: 이후 모든 요청은 로그인 세션을 전제로 처리된다. (기기: 모바일)

### 1.2 진행 중인 프로모션 목록/상세 조회 (UC-2)

**상황**: 로그인 직후 거래처 담당자가 현재 참여할 수 있는 프로모션을 확인하려 한다.

- 사용자 행동: 프로모션 목록 화면에 진입한다.
- 시스템 반응: status=게시됨 상태의 프로모션만 노출한다(BR-9). 관리자가 아직 게시하지 않았거나(임시저장) 이미 종료된 프로모션은 목록에서 보이지 않는다(BR-10).
- 사용자 행동: 관심 있는 프로모션(예: 가격 할인)을 눌러 상세 화면으로 이동한다.
- 시스템 반응: 프로모션 유형, 설명, 쿠폰 이벤트 부착 여부(있다면 잔여 정원 안내)를 보여준다.
- 결과: 담당자는 참여 신청 여부를 판단할 정보를 확보한다. (기기: 모바일)

### 1.3 일반 프로모션 참여 신청 (UC-3)

**상황**: 쿠폰 이벤트가 붙지 않은 "신제품 시식" 프로모션 상세 화면에서 참여를 결정한다.

- 사용자 행동: "참여 신청하기" 버튼을 누른다.
- 시스템 반응: (프로모션, 거래처) 조합으로 신규 Application 레코드를 상태=신청됨으로 생성한다(BR-3).
- 결과: "신청이 완료되었습니다" 안내와 함께, 내 신청 목록에 해당 건이 추가된다. (기기: 모바일)

### 1.4 쿠폰 이벤트 프로모션 참여 신청 및 즉시 추첨 (UC-3 → UC-4)

**상황**: "1+1" 프로모션에 선착순 50명 한정 쿠폰 이벤트가 부착되어 있다.

- 사용자 행동: 상세 화면에서 잔여 정원(예: 50명 중 23명 신청)을 확인하고 "참여 신청하기"를 누른다.
- 시스템 반응:
  1. 신청과 동시에 CouponEvent.applied_count를 원자적으로 1 증가시키고 마감 여부(applied_count>=50)를 판정한다(BR-6, BR-7).
  2. 신청이 성공하면 서버가 즉시 확률분포(5%=40%, 10%=30%, 15%=20%, 20%=10%)에 따라 할인율을 추첨해 DrawResult를 확정한다(BR-4).
- 결과: 화면에 당첨 할인율(예: "10% 당첨")과 유효기한(확정일로부터 1개월, BR-8)이 즉시 표시된다. 재추첨은 제공되지 않는다(BR-5). (기기: 모바일)

### 1.5 예외: 선착순 50명 마감 후 신청 시도 (EX-1, BR-6, BR-7)

**상황**: 위 1.4와 같은 쿠폰 이벤트 프로모션에 이미 50번째 신청까지 완료되어 마감된 상태다.

- 사용자 행동: 51번째로 "참여 신청하기"를 누른다(다른 담당자와 거의 동시에 눌렀을 수도 있음).
- 시스템 반응: applied_count 증가·마감 판정이 하나의 트랜잭션에서 원자적으로 처리되므로, 이미 50건이 성공한 뒤의 시도는 조건부 갱신 쿼리가 0건에 영향을 미쳐 실패로 판정된다(BR-6, BR-7).
- 결과: Application도 DrawResult도 생성되지 않고, "마감되었습니다" 안내만 표시된다(EX-1). 취소로 인해 자리가 재개방되는 일은 없다(BR-6). (기기: 모바일)

### 1.6 참여신청 취소 후 재신청 (UC-5, BR-3, BR-5, EX-2, EX-4)

**상황**: 담당자가 실수로, 또는 마음이 바뀌어 이미 신청한 쿠폰 이벤트 프로모션을 취소했다가 다시 신청하려 한다.

- 사용자 행동(1차): 내 신청 목록에서 해당 건의 "취소" 버튼을 누른다.
- 시스템 반응: 기존 Application 레코드를 새로 만들지 않고 상태만 신청됨→취소됨으로 전환한다(BR-3). 이때 CouponEvent.applied_count는 감소하지 않는다(슬롯 미반환, BR-6).
- 사용자 행동(2차): 마음이 바뀌어 동일 프로모션 상세에서 다시 "참여 신청하기"를 누른다.
- 시스템 반응: 기존 레코드가 취소됨 상태이므로 중복 신청 거부가 아니라 재신청(상태 전환: 취소됨→신청됨)으로 처리한다(EX-2, BR-3). 재신청 시점에 정원 마감 여부를 다시 확인하며, 아직 여유가 있다면 새로 추첨하여 DrawResult를 확정한다. 새 결과는 동일 application_id 레코드에 덮어써지고(upsert) 1차 신청 때의 이전 당첨 결과는 폐기된다(BR-5).
- 결과(정원 마감 시): 만약 취소해 있는 동안 다른 담당자들의 신청으로 정원이 이미 50건에 도달했다면, 재신청 자체가 거부되고 "마감되었습니다" 안내가 표시된다(EX-4, BR-5, BR-6). (기기: 모바일)

### 1.7 예외: 종료된 프로모션 - 기신청 건 취소는 가능, 신규 신청은 불가 (BR-11, EX-3, BR-10)

**상황**: 참여 신청해 두었던 프로모션을 관리자가 종료 처리했다.

- 사용자 행동(A): 내 신청 목록에서 종료된 프로모션 건을 열람한다.
- 시스템 반응: 종료된 프로모션이라도 이미 신청한 거래처의 "내 신청 목록"에서는 계속 조회되며(BR-10), 취소 버튼도 활성 상태로 제공된다. 취소를 누르면 정상적으로 상태가 취소됨으로 전환된다(BR-11).
- 사용자 행동(B): (해당 프로모션에 신청한 적 없는) 다른 담당자가 종료된 프로모션에 신규로 참여 신청을 시도한다.
- 시스템 반응: 신규 신청은 거부되고 "신청할 수 없는 프로모션입니다" 안내가 표시된다(EX-3, BR-11). 단, 이 프로모션은 애초에 "진행 중인 프로모션 목록"에는 노출되지 않으므로(BR-9), 직접 링크 등으로 상세 화면에 진입한 경우에 해당한다.
- 결과: 종료 후에도 취소 권한은 보장되지만 신규 참여는 원천 차단된다. (기기: 모바일)

### 1.8 내 참여신청 목록 조회 (UC-5, BR-8, BR-10)

**상황**: 담당자가 그동안 신청한 프로모션과 당첨 결과를 한눈에 확인하려 한다.

- 사용자 행동: "내 신청 목록" 메뉴로 이동한다.
- 시스템 반응: 신청됨/취소됨 상태와 무관하게 신청 이력 전체를 보여주며, 쿠폰 이벤트에 참여한 건은 당첨 할인율과 사용 유효기한(확정일+1개월)을 함께 표시한다(BR-8). 종료된 프로모션 건도 계속 노출된다(BR-10).
- 결과: 담당자는 별도 채널 없이 자신의 참여 이력과 혜택을 한 화면에서 확인한다. (기기: 모바일, 데스크탑에서도 반응형으로 동일하게 조회 가능)

## 2. 관리자 시나리오 (기본 기기: 데스크탑)

관리자는 식자재 유통사 사무실에서 데스크탑으로 접속하는 것을 기본으로 하되, 반응형 UI이므로 외근 중 모바일에서도 동일하게 사용할 수 있다(PRD 3절, 6.1절).

### 2.1 프로모션 게시 및 쿠폰 이벤트 설정 (UC-7, BR-9, BR-6)

**상황**: 관리자가 신규 "가격 할인" 프로모션을 거래처에 공개하려 한다.

- 사용자 행동: 관리자 화면에서 프로모션을 등록(제목/유형/설명 입력)하고, 쿠폰 이벤트를 부착할지 선택한 뒤(부착 시 정원은 50명 고정, BR-6) "게시" 버튼을 누른다.
- 시스템 반응: Promotion.status를 게시됨으로 전환한다(BR-9). 이 순간부터 거래처 담당자의 "진행 중인 프로모션 목록"에 노출된다.
- 결과: 별도 안내 채널(전화, 카톡) 없이 앱을 통해 거래처에 공식적으로 프로모션이 공개된다. (기기: 데스크탑)

### 2.2 프로모션 종료 처리 (UC-7, BR-10, BR-11)

**상황**: 프로모션 진행 기간이 끝나 관리자가 신규 신청을 마감하려 한다.

- 사용자 행동: 프로모션 관리 화면에서 해당 건의 "종료" 버튼을 누른다.
- 시스템 반응: Promotion.status를 종료됨으로 전환한다. 이후 거래처 담당자의 "진행 중인 프로모션 목록"에서는 즉시 제외되지만(BR-9, BR-10), 이미 신청한 거래처는 자신의 신청 이력을 계속 조회하고 취소할 수 있다(BR-11).
- 결과: 관리자는 신규 신청만 차단하고 기존 신청자의 조회/취소 권리는 그대로 보존한다. (기기: 데스크탑)

### 2.3 프로모션별 참여 현황 확인 (UC-8)

**상황**: 관리자가 특정 프로모션에 얼마나 반응이 있었는지 파악하려 한다.

- 사용자 행동: 프로모션 상세의 "참여 현황" 탭을 연다.
- 시스템 반응: 신청 거래처 수(신청됨/취소됨 구분 포함), 쿠폰 이벤트가 있다면 정원 대비 누적 신청 수(applied_count)와 할인율별 당첨 분포 요약을 보여준다.
- 결과: 관리자는 전화·개별 문의 없이 반응 현황을 데이터로 확인해 후속 프로모션 기획에 활용한다. (기기: 데스크탑)

## 3. 우선순위가 낮은 보조 시나리오 (Should/Could, 간략)

### 3.1 관리자: 프로모션 임시저장 (UC-6, Should)

**상황**: 관리자가 프로모션 내용을 작성하다가 완성 전에 저장만 해두고 싶다.

- 사용자 행동: 프로모션 작성 화면에서 "게시" 대신 "임시저장"을 누른다.
- 시스템 반응: Promotion.status를 임시저장 상태로 저장한다. 이 상태의 프로모션은 거래처 담당자 목록에 노출되지 않는다(BR-9).
- 결과: 별도의 전용 화면 없이도 상태값만으로 작성 중 프로모션을 관리한다(PRD 4.2절, 별도 UI 없이 축소 구현 가능). (기기: 데스크탑)

### 3.2 공통: 마이페이지 정보 조회/수정 (UC-9, Could)

**상황**: 거래처 담당자 또는 관리자가 자신의 연락처나 비밀번호를 갱신하려 한다.

- 사용자 행동: 마이페이지에서 정보를 조회하거나 이름/전화번호/비밀번호를 수정한다.
- 시스템 반응: 변경 사항을 저장하고 확인 메시지를 보여준다.
- 결과: 시간이 부족할 경우 가장 먼저 축소되는 기능이며, 최소한 읽기 전용 "내 정보 조회"만 남기는 것으로 대체될 수 있다(PRD 5절 UC-9 비고). (기기: 모바일/데스크탑 공통)

## 4. 기기별 사용 참고 (반응형 UI)

- 거래처 담당자 시나리오(1절)는 현장 모바일 사용을 기본 전제로 서술했으나, 사무실 데스크탑에서도 동일한 화면이 반응형으로 동작해야 한다(PRD 6.1절).
- 관리자 시나리오(2절)는 사무실 데스크탑 사용을 기본 전제로 서술했으나, 외근 중 모바일에서도 동일한 코드베이스의 반응형 레이아웃으로 프로모션 게시/종료·현황 확인이 가능해야 한다(PRD 3절, 6.1절).
